Migration and runtime prerequisites
1. Apply backend/migrations/003_stage1_multitenancy_and_rls.sql using the migration
   owner before deploying the Stage 1 application.
   The migration supports the original schema plus 002, and databases where the
   previous two 003 migrations have already run. Existing migrations are preserved.
2. For a new database, run the original demo seed before Stage 1. Stage 1 changes
   quality indicator uniqueness from a global code to (hospital_id, code), so the
   original seed's ON CONFLICT(code) is intended to run before that change.
3. Production DATABASE_URL must use a restricted runtime login with table DML,
   schema USAGE, and required sequence privileges. It must not be superuser,
   BYPASSRLS, or a member of hms_system. The application refuses production
   requests when the connected role bypasses RLS.
4. Reachable shared REDIS_URL is required for authentication. rediss:// uses TLS.
   Memory fallbacks are not used for token revocation or authentication sessions.
5. Preserve existing ENCRYPTION_KEY, ENCRYPTION_MASTER_KEY, versioned historical
   master keys, and SECRET_KEY. No live secret values were changed.
6. Existing sessions need a fresh sign-in to receive hospital-scoped JWT claims.
7. The published admin@hms.local demo account becomes HOSPITAL_ADMIN inside
   Demo General Hospital. Platform operators require separate provisioning.
   hms_system is a NOLOGIN maintenance role with explicit RLS policies.

Scope and limitations

or production deployment settings were changed. Live ABDM callbacks and hosted
infrastructure still require environment-specific validation. Stage 2 is pending.
